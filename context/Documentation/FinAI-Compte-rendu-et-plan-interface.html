01 / Compte rendu

Ce que fait réellement la solution

FinAlze est une chaîne de numérisation d’états financiers, avec extraction native ou OCR, structuration comptable, contrôles de cohérence, scores de qualité et revue humaine. La nouvelle interface doit rendre cette chaîne compréhensible et observable, tout en conservant la preuve d’origine.

Recommandation : conserver le moteur Python, FastAPI, Celery et Streamlit/AgGrid. Refondre le parcours et compléter les contrats serveur nécessaires : admissibilité, événements de progression, cadrage, données brutes immuables et résultats révisés persistants.

Les 152 fichiers Python de l’archive ont été analysés structurellement avec l’AST, sans erreur de syntaxe lors de cette analyse. Les chemins upload → worker → extraction → enrichissement → scoring → revue ont fait l’objet de lectures approfondies, complétées par les modèles, règles, migrations, fichiers de déploiement et éléments de documentation. L’annexe recense tous les modules applicatifs. Cela constitue une compréhension globale détaillée ; ce n’est pas une certification ligne par ligne de l’absence de défauts.

Limites : aucun service n’a été démarré, aucune extraction de document ni suite de tests applicatifs n’a été exécutée. Les 672 fonctions de test inventoriées ne sont donc pas 672 tests déclarés réussis. L’environnement virtuel de développement n’est pas fourni. Les exemples du présent dossier sont fictifs ; les documents financiers clients inclus ne sont pas reproduits. Le code applicatif n’a pas été modifié.

Deux modes à préserver

Mode local : Streamlit appelle directement FinAlzePipeline.process_document() et attend sous un spinner. Mode API : Streamlit soumet le fichier ; FastAPI le stocke puis publie une tâche ; le worker écrit le résultat ; un fragment Streamlit consulte le statut toutes les deux secondes. La refonte doit partager les mêmes états et règles entre les deux modes.

Les routes d’authentification portent encore le préfixe /auth/jwt, mais la stratégie effectivement branchée utilise des jetons opaques révocables dans Redis. Le produit ne possède pas encore un parcours de connexion nominatif dans son interface : celle-ci peut utiliser une clé, un jeton ou le compte de bootstrap fourni par l’environnement.

03 / Traitements

Le parcours actuel, de l’upload à la revue

1. Admission technique et stockage

submit_document() contrôle l’extension et la taille, stocke les octets puis crée Document et Job. La limite par défaut est de 25 Mio. L’API accepte PDF, DOCX, JPG/JPEG, PNG, TIFF et BMP ; l’upload Streamlit ne propose que PDF, DOCX, JPG/JPEG et PNG. Le type MIME enregistré vient du client ; la route ne vérifie pas encore la signature réelle du fichier ni sa nature financière.

2. Cascade de moteurs

Niveau techniqueTraitement et décisionLimite à afficher honnêtement
Tier 0Extraction native des PDF ; reconstruction géométrique de tableaux, parsing, mapping, validations. Peut court-circuiter le Tier 1 avec les cinq contrôles « green flag » et un QCS ≥ 0,95.Un moteur non exécuté doit apparaître « non nécessaire », pas « terminé ». Ces seuils sont ceux du code, pas une garantie de précision.
Tier 1Docling et OCR ; prétraitement des images, tableaux et géométrie source. Enrichissement et réconciliation avec les résultats natifs disponibles. Seuil de non-escalade par défaut : 0,75.Accepter le résultat du moteur ne signifie pas approuver le document : la revue humaine peut rester requise.
Tier 2Emplacement prévu pour un VLM.Non implémenté : retourne des données vides et un score 0. Ne pas présenter un traitement IA réellement exécuté.
Tier 3Vote entre sources disponibles, conflits, valeurs retenues et Q_table ; nouvelle validation du résultat voté.Le juge LLM de la bande intermédiaire n’est pas branché. Le consensus n’est pas une mesure d’exactitude absolue.

3. Enrichissement comptable

Le système repère les sections, attribue des rôles aux colonnes, détecte les unités, interprète les nombres et rapproche les libellés d’une nomenclature. Il conserve une représentation CanonicalTable → CanonicalRow → CanonicalCell avec valeurs, provenance, confiance et signalements.

column_binder.py utilise les en-têtes pour proposer les rôles, puis des identités arithmétiques pour les vérifier. scale_resolver.py peut choisir une interprétation numérique lorsque les contraintes permettent de l’arbitrer, ou inférer certaines valeurs manquantes avec signalement. Ces traitements changent donc certaines valeurs traitées avant l’ouverture de la revue.

statement_builder.py produit l’inventaire des états et met en quarantaine les classifications insuffisantes. Un raccordement conservateur de continuations existe déjà, malgré certains commentaires introductifs restés anciens. Dans process_document(), cet inventaire est attaché après la cascade. Il n’existe pas encore de décision documentaire précoce « non financier → arrêt ».

4. Règles et scores

FamilleRôlePrésentation cible
V1Cohérence interne : équilibre du bilan, brut/amortissement/net, compte de résultat, sous-totaux, variations, types.Valeurs attendues/observées, écarts et cellules sources.
V2Cohérence entre états : résultat, trésorerie, report à nouveau.Montrer les pièces nécessaires manquantes et les contrôles non exécutables.
V3Anomalies : signes, zéros, ordres de grandeur et proportions.Alerte à examiner, sans assimiler automatiquement une anomalie à un faux document.
V4Ratios et informations financières.Indicateurs informatifs distincts du verdict de validité.

Le catalogue comprend 15 règles. Leur exécution reste largement codée dans validate_with_rules() : charger le JSON ne signifie pas que toutes les activations, formules et limites sont dynamiques. Certaines listes de contrôles de sous-totaux et de variations sont tronquées à trois résultats par segment. La refonte doit compter les contrôles réellement exécutés et distinguer la couverture attendue.

Le QCS utilise par défaut 40 % intrinsèque + 30 % heuristique + 30 % sémantique − pénalité de corrections. Les échecs critiques et certains contrôles critiques non exécutés imposent une revue. Les vrais grades Docling sont enregistrés séparément pour calibration ; le code garde volontairement l’ancien chemin de score pour le routage. Présenter un « score OCR avant règles » exige donc un nouveau calcul clairement nommé : le QCS actuel contient déjà les règles métier.

5. Revue humaine et restitution

L’interface possède déjà trois vues — extraction, parsing avant validation, sortie corrigée —, la mise en évidence de cellules sur le document, les couleurs d’alerte, les explications des contrôles, la réévaluation, les confirmations et l’historique des corrections. Les exports JSON, CSV et Excel sont présents. La refonte doit organiser ces acquis dans un parcours guidé plutôt que les réécrire sans nécessité.

Le serveur enregistre les corrections sous forme de lignes append-only et peut changer l’état du document. Cependant, la route de résultat renvoie toujours le résultat du job : elle ne recompose pas une version finale à partir des corrections. Une validation persistée doit inclure un résultat révisé, un rapport de contrôles et une version cohérents.

05 / Parcours cible

Neuf étapes, avec un arrêt explicite dès l’admission

Votre numérotation passe de 2 à 4. Je propose d’utiliser l’étape 3 pour le contrôle bloquant (« break case »). « Cadrage » est interprété comme une identification des pages/zones et des champs attendus, avec confirmation humaine lorsque nécessaire.

Une dépendance technique à respecter : sur un scan, reconnaître le type financier nécessite déjà une lecture OCR. La préanalyse peut donc effectuer une lecture légère avant le cadrage, puis réutiliser ses résultats pour l’extraction. Aucun rejet « aucun état financier » ne doit être déduit du seul nom de fichier ou des premières pages d’un long rapport.

Proposition de périmètre initial : bilan et compte de résultat. Les tableaux de flux déjà détectables seront identifiés et signalés ; leur admission isolée et leur validation complète sont à confirmer. Un document partiel contenant un véritable état est « admissible, incomplet » et non « non financier ». Les contrôles impossibles faute d’une autre pièce restent visibles.

Terminologie L1 proposée : première couche d’extraction brute, indépendante du numéro de moteur. Ainsi, un PDF lu nativement conserve sa voie Tier 0. Si vous entendez par L1 « exécuter obligatoirement le moteur Tier 1 », cette contrainte devra être confirmée, car elle change coûts et délais.

06 / Break case

Arrêter pour une cause précise, au bon moment

Au démarrage de l’application

Afficher « Prêt à analyser » seulement si l’API, le stockage et la file de traitement sont utilisables ; si le worker ne répond pas, indiquer « En attente du service de traitement » et la politique de mise en file. L’interface explique d’emblée que seuls les documents du périmètre financier sont admissibles. Une vérification du contenu ne peut se faire qu’après le dépôt.

Conditions du rejet sémantique : couverture suffisante des pages, lecture exploitable, aucun état admis détecté et décision traçable. Tant qu’une portion illisible pourrait contenir l’état recherché, choisir « indéterminé ». Les seuils de cette décision devront être calibrés avec un jeu positif/négatif revu humainement ; aucun seuil de précision n’est inventé dans ce dossier.

Après arrêt, les étapes suivantes restent « non exécutées ». Les actions sont « Remplacer le fichier », « Voir la cause » et, si prévu par les droits, « Demander une revue ». Une demande de revue ne constitue pas une approbation automatique.

08 / Contrat de progression

Afficher uniquement ce que le moteur peut confirmer

Une barre pilotée par un minuteur donnerait une fausse précision. Le serveur doit produire des événements avec : job_id, attempt, event_seq, stage, status, completed_units, total_units, unit_type, started_at, updated_at, reason_code et une référence de résultat.

PostgreSQL conserve l’état de référence et le journal de progression. Streamlit peut garder son rafraîchissement à deux secondes et demander uniquement les événements nouveaux. Un flux SSE pourra être ajouté ultérieurement si nécessaire ; il n’est pas indispensable à la première refonte.

Reprises, annulation et pertes de connexion

Les compteurs sont monotones à l’intérieur d’une tentative. Une reprise crée une nouvelle tentative visible ; des événements en retard ne peuvent pas réactiver un job terminé. Une perte de connexion affiche « Suivi interrompu, traitement serveur potentiellement actif ». Après rechargement de la page, le dossier est retrouvé par identifiant et organisation.

La demande d’annulation passe par le serveur. Le worker s’arrête entre unités sûres ; un appel moteur non interruptible peut retarder la confirmation. Les écritures finales vérifient toujours l’état pour qu’un succès tardif ne remplace pas une annulation confirmée. Les nouvelles tentatives d’erreurs techniques sont bornées ; les rejets métier ne sont pas relancés automatiquement.

Régression de l’extraction

Utiliser le mécanisme existant tools/golden_sweep.py snapshot / compare / facts. Pour chaque changement modifiant l’extraction, déclarer les différences attendues et refuser les autres. Le journal de variations doit être dirigé hors du dépôt via FINALZE_VARIATION_LOG, conformément aux instructions du projet. Les corpus clients restent dans l’environnement autorisé ; aucune génération de référence externe n’est requise pour cette refonte.

Conditions de livraison

  • Chaque statut affiché est justifié par une donnée serveur ; aucun faux pourcentage ni faux succès de sauvegarde.
  • Un document non admissible s’arrête avec une cause ; un financier mal lu n’est pas rejeté comme non financier par défaut.
  • Les valeurs brutes demeurent identiques ; les transformations et interventions humaines sont consultables.
  • Les étapes cadrage → extraction → règles → revue sont explicites et reprenables.
  • La validation et les exports correspondent à une version persistée, avec protection contre les modifications concurrentes.
  • Les tests ciblés et les régressions nécessaires passent ; le rapport de livraison indique aussi les limites restantes.
